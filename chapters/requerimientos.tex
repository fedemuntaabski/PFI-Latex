\section{Alcance del relevamiento}
\label{sec:alcance-relevamiento}

Esta sección presenta el análisis funcional del sistema, compuesto por tres elementos: un agente local que actúa como Punto de Cumplimiento de Políticas (PEP) y recolecta telemetría de actividad; una API central que funciona como Punto de Decisión de Políticas (PDP) y calcula un puntaje de riesgo (\emph{score}) dinámico mediante un modelo híbrido Isolation Forest + LSTM Autoencoder; y un \emph{dashboard} para visualizar el estado de los usuarios y administrar las políticas. La separación entre los puntos de decisión y aplicación de políticas sigue los lineamientos de NIST SP 800-207 \parencite{Rose2020}.

El análisis se organiza en cuatro casos de uso que abarcan la lógica de negocio del sistema: detección y mitigación (CU-01), ajuste de políticas (CU-02), reentrenamiento periódico del modelo (CU-03) y alta de usuarios nuevos con período de aprendizaje (CU-04). La integración con sistemas de gestión de identidad (IAM) se aborda como un módulo transversal.

\section{Actores del sistema}
\label{sec:actores}

En el sistema intervienen siete actores: tres humanos, tres internos y uno externo.

Entre los actores humanos, el administrador de seguridad opera el \emph{dashboard} con el rol \textit{admin}. Sus funciones incluyen monitorear a los usuarios, ajustar umbrales y políticas, configurar el reentrenamiento y consultar la auditoría. El analista de seguridad accede con el rol \textit{operador}, de solo lectura, y consulta el historial y las explicaciones de los puntajes para fundamentar decisiones posteriores. Por su parte, el usuario monitoreado es un actor indirecto: genera actividad en su \emph{endpoint} y constituye el sujeto de observación, pero no interactúa directamente con el sistema.

Los actores internos son el agente local (PEP), que recolecta metadatos de actividad, los envía a la API y ejecuta y confirma las acciones de mitigación en el \emph{endpoint}; la API de \emph{scoring} (PDP), que calcula el puntaje de riesgo, aplica el decaimiento temporal, asigna el nivel de riesgo y decide la acción de mitigación; y el planificador del sistema, que activa el reentrenamiento periódico del modelo según la periodicidad configurada. Finalmente, el proveedor IAM es un sistema externo que proporciona, de forma opcional, el rol y el departamento del usuario monitoreado.

\section{Casos de uso}
\label{sec:casos-de-uso}

Esta sección describe los cuatro casos de uso del sistema: la detección de desviaciones conductuales con mitigación automática en el \emph{endpoint} (CU-01), el ajuste de umbrales y políticas de respuesta (CU-02), el reentrenamiento periódico del modelo (CU-03) y el alta de usuarios nuevos con período de aprendizaje (CU-04). Para cada uno se describen los actores, el disparador y las precondiciones, el flujo principal y sus alternativas, el resultado esperado y los requerimientos e historias de usuario con que se vincula.

\subsection{CU-01: Detección de desviación conductual y mitigación automática en el endpoint}
\label{sec:cu01}

El actor principal de este caso de uso es el agente local (PEP), mientras que la API de \emph{scoring} (PDP) actúa como actor secundario. El caso se inicia cuando el usuario realiza una actividad en el equipo monitoreado: ejecuta un proceso, crea, modifica, renombra o elimina un archivo en una carpeta vigilada, o se conecta a un recurso de red. Como precondiciones, el agente debe estar instalado y autenticado ante la API mediante su clave, y los modelos deben estar cargados.

El flujo comienza cuando el agente captura el evento y lo envía a la API. Esta valida su estructura, descarta los reenvíos duplicados, actualiza el estado del usuario y persiste el evento sin procesar. Luego calcula el puntaje de riesgo mediante el modelo híbrido, lo combina con la línea base personal del usuario, aplica el decaimiento temporal y asigna el nivel correspondiente según los umbrales vigentes y la regla de piso. A continuación, genera la explicación del puntaje y determina la acción de mitigación según el mapeo nivel $\rightarrow$ acción.

Si hay un proveedor IAM configurado, la API también consulta el rol y el departamento del usuario, utilizando caché y mecanismos de tolerancia a fallas. Esta integración es opcional y está desactivada por defecto. La información obtenida se muestra en el detalle del usuario en el \emph{dashboard}, pero no interviene en el cálculo del puntaje. Una vez completado el procesamiento, la API responde al agente con el puntaje, el nivel de riesgo y la acción correspondiente. El agente ejecuta esta última localmente y, si modifica el equipo, confirma el resultado a la API. Además, cuando el nivel asignado tiene habilitadas las notificaciones, la API envía un correo al administrador antes de responder. Si el envío falla, la respuesta no se ve afectada; sin embargo, una demora del servidor de correo puede retrasarla.

El flujo contempla cuatro situaciones alternativas. Si la API no está disponible, el agente almacena el evento en el \emph{buffer} local y reintenta el envío. Si la API rechaza la clave del agente, se activa el \emph{circuit breaker} y el reenvío de los eventos pendientes pasa a realizarse mediante sondeos cada cinco minutos, mientras el agente continúa monitoreando la actividad. Si el evento corresponde a un usuario nuevo, el cálculo del puntaje sigue el flujo definido en CU-04. Por último, si el sistema operativo no permite ejecutar la acción de mitigación, el agente informa el error y este queda registrado.

Al finalizar, el evento queda registrado y su puntaje, nivel, acción y explicación se conservan en la lista acotada de eventos recientes. Además, el último evento de cada día se incorpora al historial diario. El resultado de la mitigación, tanto si se aplica correctamente como si falla, queda reflejado en la última confirmación de acción del usuario.

Este caso de uso se relaciona con los requerimientos RF-01 a RF-11 y RF-28 a RF-30, así como con las historias de usuario HU-01 a HU-04, HU-15 y HU-16. Su principal valor diferencial es que integra la detección, la decisión y la ejecución de la acción de mitigación en el propio \emph{endpoint}, sin intermediarios ni necesidad de un nuevo inicio de sesión. Esto contrasta con las soluciones analizadas en el estado del arte, que detectan y generan alertas, pero delegan la respuesta.

\subsection{CU-02: Ajuste de umbrales y políticas de respuesta}
\label{sec:cu02}

El actor principal es el administrador de seguridad, quien necesita ajustar la sensibilidad del sistema y definir las respuestas asociadas a cada nivel de riesgo. La única precondición es haber iniciado sesión en el \emph{dashboard}.

Desde el \emph{dashboard}, el administrador consulta el estado de los usuarios y la configuración vigente. A partir de esta información, puede modificar los umbrales de riesgo, la cantidad de niveles, las acciones asociadas a cada uno y los niveles para los que se deben generar notificaciones. Una vez enviados los cambios a la API, esta valida la coherencia de la política, verificando que los rangos sean contiguos, que la cantidad de niveles sean 4, y que las acciones y la regla de piso sean consistentes con los niveles definidos. Si la configuración es válida, la API persiste la nueva política, registra el cambio en la auditoría y aplica la configuración actualizada a la evaluación de los eventos siguientes.

El caso de uso contempla dos flujos alternativos. Si el token de sesión es inválido, está vencido o pertenece a un usuario sin permisos de administración, la API rechaza la operación con un código HTTP 401 o 403, según corresponda. La autorización se verifica siempre en la API, a partir del rol asociado al token, por lo que la sesión del \emph{dashboard} no sustituye esta validación. Por otro lado, si la configuración no cumple las reglas establecidas, la API rechaza el cambio e informa el motivo mediante un mensaje específico, sin modificar la política vigente.

Como resultado, la nueva política queda activa sin necesidad de reiniciar los servicios y el cambio queda registrado en la auditoría. Este caso de uso se relaciona con los requerimientos RF-12 a RF-17 y RF-31, así como con las historias de usuario HU-05 a HU-07 y HU-14. Su principal aporte es permitir que el administrador adapte la configuración a distintos contextos de seguridad sin depender del equipo de desarrollo y defina respuestas graduales según el nivel de riesgo, en línea con la preferencia por medidas menos disruptivas identificada en la encuesta (sección~\ref{sec:encuesta-usuarios}).

\subsection{CU-03: Reentrenamiento periódico del modelo}
\label{sec:cu03}

El actor principal es el planificador del sistema, mientras que el administrador de seguridad participa como actor secundario. El caso de uso se activa cuando se cumple el período configurado desde el último reentrenamiento registrado, siempre que el planificador se encuentre dentro de la ventana horaria definida. Como precondiciones, el reentrenamiento automático debe estar habilitado y deben existir eventos crudos registrados en la base de datos. Sin embargo, el planificador no verifica si se incorporaron eventos nuevos desde el último entrenamiento.

Cuando detecta que corresponde reentrenar, el sistema exporta los eventos crudos acumulados junto con el conjunto de datos original, adaptándolos al formato requerido por el \emph{pipeline} de entrenamiento. Este se ejecuta en un proceso aislado. Una vez generado el nuevo modelo, el sistema evalúa tanto este como el modelo vigente sobre los mismos escenarios de referencia. Si el nuevo modelo cumple el criterio de promoción, es decir, si su desempeño no resulta inferior al permitido, se incorpora como modelo vigente sin necesidad de reiniciar la API. Finalmente, el sistema registra el reentrenamiento, incluyendo la fecha, los eventos utilizados y la variación de las métricas obtenidas.

Como alternativa al disparo automático, el administrador de seguridad puede registrar manualmente un reentrenamiento realizado fuera del planificador. Si se produce un fallo en algún paso del \emph{pipeline}, se restauran los artefactos del modelo vigente, que continúa en servicio. En este caso, el intento queda registrado en el historial con la leyenda \emph{pipeline en curso}, que no se actualiza posteriormente, y el próximo reentrenamiento se dispara cuando vuelve a cumplirse el período configurado, contado desde ese intento. En cambio, si el intento finaliza por una excepción, no se registra y el planificador vuelve a intentarlo en el siguiente chequeo, cinco minutos después. Ambos comportamientos se encuentran identificados como correcciones previstas (sección~\ref{sec:sintesis-limitaciones}).

Por otra parte, si el nuevo modelo no cumple el criterio de promoción, faltan escenarios de referencia, el corte temporal no coincide con el esperado o se produce un error durante el cálculo de las métricas, el sistema rechaza la promoción, conserva el modelo vigente y registra el motivo del rechazo.

Al finalizar el proceso, el modelo vigente se mantiene o se actualiza según el resultado de la evaluación, y el reentrenamiento queda registrado cuando corresponde. Este caso de uso se relaciona con los requerimientos RF-18 a RF-22 y con las historias de usuario HU-08 a HU-10. Su principal aporte es reducir el riesgo de degradación del modelo ante el \emph{concept drift}, mediante reentrenamientos periódicos y una evaluación previa a la promoción, sin interrumpir el servicio ni incorporar modelos cuyo desempeño supere el margen de degradación permitido.

\subsection{CU-04: Alta de usuario nuevo y período de aprendizaje (cold-start)}
\label{sec:cu04}

Los actores principales son el agente local y la API, mientras que el administrador de seguridad participa como actor secundario. El caso de uso se activa cuando la API recibe el primer evento de un usuario que aún no está registrado. Como precondición, el agente local debe estar operativo en el equipo del usuario.

Al detectar que el usuario no está registrado, la API crea su estado y lo establece en modo de aprendizaje, de acuerdo con el umbral configurado. Durante este período, los eventos se evalúan normalmente, pero la acción de mitigación se aplica de forma atenuada. A su vez, el \emph{dashboard} muestra al usuario en aprendizaje e informa su progreso. Una vez alcanzado el umbral establecido, el sistema lo incorpora automáticamente al monitoreo normal. Si el administrador modifica el umbral durante el aprendizaje, el cambio se aplica a partir del siguiente evento. Sin embargo, cuando un evento afecta a un recurso sensible, se aplica la política normal, sin atenuar la acción de mitigación.

Al finalizar el caso de uso, el usuario deja el modo de aprendizaje y las acciones se aplican sin atenuación, según el mapeo configurado. No obstante, la cobertura del puntaje puede seguir siendo parcial hasta que se completen los 50 eventos requeridos por el modelo LSTM (RF-03). Este caso de uso se relaciona con los requerimientos RF-23 a RF-27 y con las historias de usuario HU-11 a HU-13. Su principal aporte es reducir los falsos positivos durante la incorporación de nuevos usuarios, asociados al problema de \emph{cold-start}, una limitación documentada en la literatura \parencite{VillarrealVasquez2021, Benova2024}.

\section{Historias de usuario}
\label{sec:historias-usuario}

Las historias de usuario se expresan con el formato ``Como [rol], quiero [funcionalidad], para [beneficio]'', y sus criterios de aceptación se derivan de la estructura ``Dado / Cuando / Entonces''. Se agrupan en cinco épicas alineadas con los casos de uso.

\subsection{Épica 1: Detección y respuesta en el endpoint (CU-01)}

Esta épica reúne las historias asociadas a CU-01: la recolección de actividad, el puntaje de riesgo por evento, la mitigación automática y la reversión de acciones.

\textbf{HU-01: Recolección de actividad en el endpoint.} Como administrador de seguridad, quiero que el agente recolecte en segundo plano la actividad de procesos, archivos, aplicaciones y red de cada equipo, para contar con la información necesaria para evaluar el comportamiento sin interrumpir al usuario. La historia se considera cumplida cuando, con un agente instalado, cada proceso ejecutado o archivo accedido por el usuario llega a la API como evento con identificador de usuario, tipo y marca temporal; cuando, si la API no responde, el evento queda en el \emph{buffer} local y se envía al restablecerse la conexión; y cuando ningún evento incluye contenido de archivos, capturas de pantalla ni pulsaciones de teclado.

\textbf{HU-02: Puntaje de riesgo por evento.} Como administrador de seguridad, quiero que cada evento reciba un puntaje de riesgo y un nivel, para saber en tiempo casi real cuánto se desvía un usuario de su conducta esperada. Ante un evento válido, la API debe devolver un puntaje entre 0 y 100 y el nivel que corresponde a los umbrales vigentes. Cuando un usuario vuelve tras un período sin actividad, su riesgo acumulado debe haberse reducido por decaimiento temporal, y cuando al menos uno de los dos modelos marca anomalía, el nivel no debe quedar por debajo del piso, que por defecto es alto.

\textbf{HU-03: Mitigación automática.} Como administrador de seguridad, quiero que el agente aplique automáticamente la acción definida para cada nivel, para contener un posible compromiso sin depender de una intervención manual. Si un nivel está mapeado a \texttt{terminar\_y\_denegar}, al evaluarse el evento el agente debe terminar el proceso y denegar el acceso a la carpeta. Toda acción que modifica el equipo debe confirmarse a la API, y al usuario que mantiene la sesión abierta no debe solicitársele un nuevo inicio de sesión.

\textbf{HU-04: Reversión de acciones.} Como administrador de seguridad, quiero revertir las acciones de mitigación aplicadas, para restituir el acceso ante un falso positivo. Al ejecutarse la reversión, un permiso de carpeta denegado debe volver a su estado original y un proceso suspendido debe reanudarse; para un proceso terminado, en cambio, el resultado de la acción debe indicar que no es reversible.

\subsection{Épica 2: Panel de administración y políticas (CU-02)}

Esta épica reúne las historias asociadas a CU-02: el estado de riesgo de los usuarios, la configuración de umbrales, niveles y acciones, y las notificaciones y la auditoría.

\textbf{HU-05: Estado de riesgo de los usuarios.} Como administrador de seguridad, quiero ver en el \emph{dashboard} el estado de riesgo de cada usuario y su historial, para priorizar qué casos revisar. Al ingresar al \emph{dashboard}, cada usuario debe aparecer con su puntaje, nivel y estado de aprendizaje, y al abrir su detalle deben mostrarse sus eventos recientes con la explicación de cada puntaje.

\textbf{HU-06: Configuración de umbrales, niveles y acciones.} Como administrador de seguridad, quiero configurar umbrales, cantidad de niveles y acción por nivel, para adaptar el sistema al contexto de seguridad de la organización. Un cambio de umbrales válido, una vez guardado, debe aplicarse a la evaluación de los eventos siguientes, mientras que un cambio con rangos solapados, con menos de 3 o más de 6 niveles, o con una acción asignada a un nivel inexistente debe rechazarse con un mensaje específico.

\textbf{HU-07: Notificaciones y auditoría.} Como administrador de seguridad, quiero recibir notificaciones por correo en los niveles que elija y consultar la auditoría de cambios, para enterarme de los casos relevantes y saber cuándo, qué y con qué rol o clave se modificó la política. Cuando un usuario alcanza un nivel marcado para notificar, debe enviarse un correo con el puntaje, el nivel y los eventos recientes, con un máximo de uno por usuario dentro del intervalo mínimo (10 minutos por defecto). Todo cambio de política, a su vez, debe quedar registrado con fecha y valores en la vista de auditoría.

\subsection{Épica 3: Ciclo de vida del modelo (CU-03)}

Esta épica reúne las historias asociadas a CU-03: la planificación del reentrenamiento, el reentrenamiento aislado con promoción controlada y el historial de reentrenamientos.

\textbf{HU-08: Planificación del reentrenamiento.} Como administrador de seguridad, quiero configurar cada cuánto y en qué franja horaria se reentrena el modelo, para que el reentrenamiento no interfiera con el entorno productivo. Un período de entre 1 y 365 días y una ventana horaria válida deben quedar persistidos al guardarse, y un valor fuera de rango o con formato inválido debe rechazarse.

\textbf{HU-09: Reentrenamiento aislado y promoción controlada.} Como administrador de seguridad, quiero que el modelo se reentrene automáticamente con los eventos nuevos y solo se reemplace si no detecta peor que el vigente, para incorporar cambios de comportamiento sin degradar la detección más allá del margen tolerado ni arriesgar el servicio. Cumplido el período, el planificador debe ejecutar el \emph{pipeline} en un proceso aparte. Un modelo nuevo que satisface el criterio de no inferioridad sobre los escenarios de referencia debe reemplazar al vigente sin reiniciar la API; si no lo satisface, o si la evaluación queda incompleta, debe conservarse el vigente y registrarse el motivo.

\textbf{HU-10: Historial de reentrenamientos.} Como administrador de seguridad, quiero ver el historial de reentrenamientos, para auditar cómo evolucionó el modelo. Para cada reentrenamiento finalizado, el \emph{dashboard} debe mostrar la fecha, los eventos utilizados, la variación de métricas y el actor, y debe permitir registrar los reentrenamientos realizados manualmente.

\subsection{Épica 4: Alta de usuarios y cold-start (CU-04)}

Esta épica reúne las historias asociadas a CU-04: el período de aprendizaje, el seguimiento de los usuarios en aprendizaje y la transición automática al monitoreo normal.

\textbf{HU-11: Período de aprendizaje.} Como administrador de seguridad, quiero que los usuarios nuevos se den de alta automáticamente y atraviesen un período de aprendizaje con acciones atenuadas, para evitar bloquear a alguien solo por no tener historial. Al llegar el primer evento de un identificador nuevo, debe crearse su estado en aprendizaje. Mientras dure ese período, la acción debe atenuarse sin alterar el nivel informado, salvo en los eventos sobre recursos sensibles, a los que se aplica la política normal.

\textbf{HU-12: Seguimiento de usuarios en aprendizaje.} Como administrador de seguridad, quiero ver qué usuarios están en aprendizaje y su progreso, y ajustar el umbral, para saber qué puntajes son todavía preliminares. Para cada usuario en aprendizaje, el \emph{dashboard} debe mostrar un indicador con los eventos acumulados sobre el umbral, y un nuevo umbral entre 1 y 1000, una vez guardado, debe aplicarse desde el evento siguiente.

\textbf{HU-13: Transición automática a monitoreo normal.} Como administrador de seguridad, quiero que la salida del aprendizaje sea automática, para no tener que habilitar manualmente a cada usuario. Cuando un usuario alcanza el umbral, debe pasar a monitoreo normal y su indicador debe desaparecer del \emph{dashboard}.

\subsection{Épica 5: Requerimientos transversales}

Esta épica reúne las historias que no dependen de un único caso de uso: la autenticación de acceso a la configuración, la explicación persistida de cada puntaje y el contexto organizacional obtenido del IAM.

\textbf{HU-14: Autenticación de acceso y configuración.} Como administrador de seguridad, quiero que el acceso al \emph{dashboard} y a la configuración requiera autenticación, para que nadie sin autorización modifique las políticas. Un usuario sin sesión iniciada no debe acceder al \emph{dashboard}, y la API debe rechazar toda operación de configuración que no presente un token de sesión vigente con rol administrador, así como cualquier token cuya sesión se haya cerrado o haya vencido.

\textbf{HU-15: Explicación persistida.} Como analista de seguridad, quiero que la explicación de cada puntaje quede guardada en el historial, para poder justificar una decisión tiempo después, aunque el modelo se haya reentrenado. La explicación y el motivo de cada evento evaluado deben persistirse en el historial, y un reentrenamiento posterior no debe recalcular las explicaciones ya guardadas.

\textbf{HU-16: Contexto organizacional desde el IAM.} Como administrador de seguridad, quiero que el sistema obtenga el rol y el departamento del usuario desde el IAM de la organización, para ver en el \emph{dashboard} el contexto organizacional existente. Con un proveedor IAM configurado, la llegada de un evento de un usuario sin datos en caché debe provocar la consulta del rol y el departamento y su almacenamiento en caché. Si el proveedor no responde, el evento debe evaluarse igualmente, sin contexto IAM.
