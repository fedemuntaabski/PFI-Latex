\label{chap:arquitectura}

\section{Arquitectura lógica}
\label{sec:arquitectura-logica}
La arquitectura sigue la separación entre el punto de decisión de políticas (PDP) y el punto de aplicación de políticas (PEP) propuesta por NIST SP~800-207 \parencite{Rose2020}. El agente local actúa como PEP: observa la actividad, la informa y aplica la decisión, pero no evalúa el riesgo. La API central actúa como PDP: concentra el modelo, la política vigente y el estado de cada usuario, y decide la acción. Esta separación permite cambiar el modelo o la política sin modificar los agentes instalados.

El sistema no es una aplicación monolítica sino un conjunto de componentes con funciones y entornos de ejecución distintos, organizados en un único repositorio con cinco subsistemas: la API de \emph{scoring}, el agente, el \emph{dashboard}, el \emph{pipeline} de entrenamiento y los \emph{scripts} de validación. La API es el único punto de acceso al estado y a la configuración, y la utilizan cuatro tipos de consumidores con distintos niveles de acceso:
\begin{itemize}
	\item \textbf{Agente:} envía eventos y confirma las acciones ejecutadas, con una clave propia, ligada a su identificador y a los usuarios que puede reportar, que solo habilita esas dos operaciones.
	\item \textbf{\emph{Dashboard} en modo consulta:} lee el estado de los usuarios, el historial y la configuración.
	\item \textbf{\emph{Dashboard} en modo administración:} además, modifica la configuración y reinicia usuarios.
	\item \textbf{Público:} solo accede a la salud del servicio y al inicio y cierre de sesión.
\end{itemize}

El flujo principal comienza en el agente, que captura un evento y lo envía a la API. La API lo valida, actualiza el estado del usuario en Redis, persiste el evento crudo en PostgreSQL, calcula el puntaje y responde con el nivel y la acción. El agente ejecuta la acción y, si modifica el equipo, confirma el resultado. En paralelo, el \emph{dashboard} consulta periódicamente la API para mostrar el estado actualizado, y el planificador de la API dispara el reentrenamiento cuando corresponde.

\section{Lenguajes de programación}
\label{sec:lenguajes}
El lenguaje principal del sistema es Python, que se utiliza en la API, el agente, el \emph{pipeline} de entrenamiento y los \emph{scripts} de validación. La elección responde en primer lugar al ecosistema de aprendizaje automático empleado, basado en scikit-learn y TensorFlow, y en segundo lugar a que usarlo también en la API permite reutilizar el código de cálculo del puntaje validado durante el entrenamiento, sin reimplementarlo en otro lenguaje. Esto reduce el riesgo de diferencias entre lo que se valida y lo que se ejecuta en producción. El desarrollo se realiza con Python~3.12, mientras que la integración continua y el servidor utilizan Python~3.11.

El \emph{dashboard} se desarrolla en TypeScript, un lenguaje que incorpora tipado estático para detectar errores de tipos durante el desarrollo. Esto resulta especialmente útil porque desde la interfaz se modifican parámetros que afectan el comportamiento del agente, como los umbrales de riesgo y las acciones asociadas a cada nivel. Además, se utiliza Zod, una biblioteca de validación que permite comprobar en tiempo de ejecución que los datos recibidos desde la API tengan la estructura y los tipos esperados. Así, ambas herramientas permiten detectar errores tanto durante el desarrollo como al procesar las respuestas del sistema.

Para automatizar las tareas específicas de cada entorno, se utilizan distintos lenguajes y herramientas. PowerShell, integrado en Windows, permite configurar el inicio automático del agente y publicar en la nube las nuevas versiones de la API desde el equipo de desarrollo. Por su parte, la infraestructura en la nube se define mediante HCL, el lenguaje utilizado por Terraform para describir y gestionar los recursos. Esta configuración se complementa con \emph{scripts} en Bash, que ejecutan las tareas necesarias para preparar el servidor durante su primer arranque.

Se descartó un \emph{backend} en Node.js porque igualmente habría requerido un servicio en Python para los modelos, y Java con Spring Boot porque implica más configuración y código para el alcance del proyecto.

\section{Frameworks y librerías}
\label{sec:frameworks}

\subsection{API de \emph{scoring}}
La API se desarrolla con FastAPI y se ejecuta sobre Uvicorn. Este \emph{framework} ofrece soporte para operaciones asincrónicas, valida automáticamente los datos de entrada y salida, y genera la documentación OpenAPI a partir del código. Estas características resultan especialmente útiles para una API que cuenta con 32 \emph{endpoints}, ya que permiten mantener sus interfaces documentadas y reducir la necesidad de incorporar extensiones adicionales, como ocurriría con Flask. Por su parte, los contratos de datos compartidos entre el agente, la API y el \emph{dashboard} se definen mediante Pydantic~2, que permite validar la estructura y los tipos de los datos recibidos y rechazar los eventos mal formados sin necesidad de implementar manualmente esas validaciones.

El estado de cada usuario se guarda en Redis mediante redis-py. Se prefiere Redis frente a PostgreSQL para este fin porque el patrón de acceso es de alta frecuencia y baja latencia, y porque sus transacciones optimistas permiten a la API resolver escrituras concurrentes con hasta 20 reintentos. El historial y los eventos crudos se persisten en PostgreSQL con SQLAlchemy y psycopg2, usando consultas SQL explícitas, un grupo de conexiones reducido y tiempos de espera acotados para que una caída de la base de datos no bloquee la evaluación de eventos.

Para el desarrollo de los modelos se utilizan scikit-learn~1.4 y TensorFlow~2.16 con Keras. Scikit-learn proporciona la implementación de Isolation Forest, elegido por su bajo costo computacional frente a otras alternativas, como los autoencoders tabulares y las máquinas de vectores de soporte de una clase, y porque permite explicar los resultados a partir de las variables que más influyen en ellos. Por su parte, TensorFlow con Keras se utiliza para implementar el LSTM Autoencoder, seleccionado por su capacidad para modelar el orden de los eventos, a diferencia de Isolation Forest, que trabaja con agregados diarios. Sin embargo, la evaluación muestra que el modelo entrenado no logra aprovechar esa información temporal (sección~\ref{sec:limitaciones-producto}). Se prefiere Keras frente a PyTorch por su API de alto nivel.

El procesamiento complementario se realiza con pandas, NumPy, SciPy y joblib, que permiten manipular datos, efectuar cálculos numéricos y serializar los modelos. Las dependencias de la API se fijan en versiones exactas para favorecer la reproducibilidad de los resultados, y las pruebas automatizadas se implementan con pytest.

\subsection{Agente}
El agente depende únicamente de tres librerías externas: psutil, para enumerar procesos y conexiones de red sin invocar directamente la API de Windows; requests, para enviar los eventos a la API en forma secuencial, por lo que no necesita un cliente asincrónico; y python-dotenv, para cargar la configuración local, como la dirección de la API y su clave. Las mitigaciones de denegación y su reversión modifican los permisos de carpetas con icacls, herramienta nativa de Windows. Dado que el agente se ejecuta en segundo plano directamente en el equipo del usuario, mantener pocas dependencias limita la superficie de ataque y el consumo de recursos.

\subsection{\emph{Dashboard}}
El \emph{dashboard} se desarrolla con React~19, que permite reutilizar componentes entre pantallas, como los indicadores de nivel de riesgo, cobertura y aprendizaje. Para construir la aplicación se utiliza Vite~8, que agiliza el arranque del entorno de desarrollo y la recarga de cambios. Los datos recibidos de la API se validan con Zod~4, que complementa el tipado estático de TypeScript mediante verificaciones en tiempo de ejecución.

Las consultas a la API se gestionan con TanStack Query~5, que centraliza el caché, la revalidación y la actualización periódica de los datos cada dos segundos, evitando implementar manualmente la lógica de carga y error en cada solicitud. También permite reflejar de inmediato los cambios de configuración recién guardados. La navegación entre las ocho pantallas, incluidas las rutas protegidas por el inicio de sesión, se implementa con React Router~7. Para completar la interfaz, Recharts~3 permite representar la evolución del puntaje, mientras que Tailwind CSS~4 gestiona los estilos y los temas claro y oscuro. Por último, Oxlint se utiliza para el análisis estático del código y se integra en el proceso de integración continua.

\subsection{\emph{Pipeline} de entrenamiento}
Las seis fases del \emph{pipeline}, desde la exploración hasta el puntaje híbrido, se implementan como \emph{notebooks} de Jupyter, ya que el trabajo de preparación y entrenamiento es exploratorio e iterativo y este formato conserva el código junto con sus resultados. Cuando el planificador dispara un reentrenamiento, nbconvert ejecuta los \emph{notebooks} sin interfaz en un proceso separado de la API. Para consultar el conjunto de datos, de 14~GB en formato JSON por líneas, se emplea DuckDB, que permite ejecutar SQL sobre el archivo sin cargarlo en memoria ni administrar un motor de base de datos aparte.

\section{Servicios e infraestructura}
\label{sec:servicios}
El estado operativo y la configuración del sistema se almacenan en Redis, y el historial, los eventos crudos, la auditoría y las métricas en PostgreSQL. Ambos se contratan como servicios gestionados, Upstash para Redis y Supabase para PostgreSQL, lo que evita administrar instancias propias y los hace accesibles tanto desde el entorno local como desde la nube. Supabase aporta además seguridad a nivel de fila y la extensión criptográfica que utiliza la cadena de \emph{hashes}.

Para el despliegue se recurre a Amazon Web Services, que provee la instancia de cómputo de la API, el almacenamiento de objetos para el \emph{dashboard} y las versiones publicadas, el almacén de parámetros para los secretos y la administración remota sin SSH. El \emph{dashboard} y la API se publican con HTTPS mediante un proxy inverso (Caddy) que corre en la propia instancia. Los recursos de la nube se definen con Terraform, de modo que se crean, modifican y destruyen de forma reproducible y revisable, y GitHub Actions ejecuta en cada cambio el análisis estático, la compilación, las pruebas y la validación de la infraestructura.

Por último, el sistema integra tres servicios opcionales. El envío de correo por SMTP permite notificar al administrador y, si no hay un servidor configurado, la notificación solo se registra. Gemini asiste en la redacción del correo, con un texto predefinido de respaldo para que la notificación no dependa de un servicio externo. El adaptador de identidad admite proveedores IAM simulados, Keycloak y Microsoft Entra ID; Keycloak actúa como proveedor de referencia, está validado contra un servidor real y, como el resto, está desactivado por defecto, salvo en el despliegue en la nube. Además de leer el rol y el departamento, el adaptador informa al proveedor el nivel de riesgo y, en nivel crítico, solicita el cierre de las sesiones del usuario.

\subsection{Despliegue local}

El agente se comunica con la API por loopback y el \emph{dashboard} la consulta desde el servidor de desarrollo. Opcionalmente, la API consulta un proveedor IAM simulado o Keycloak. \subsection{Despliegue en la nube}\label{sec:despliegue-nube}

La configuración incorpora varias medidas de seguridad. La API escucha únicamente en la interfaz local de la instancia, por lo que las solicitudes externas deben pasar por el proxy. Además, el acceso a los metadatos de la instancia requiere la versión 2 del servicio y el disco se encuentra cifrado. Los secretos se almacenan en el servicio de parámetros del proveedor, en lugar de incluirse en el código, mientras que las tareas de administración y publicación de versiones se realizan mediante el almacenamiento de objetos y AWS Systems Manager (SSM), sin necesidad de habilitar el acceso por SSH.

Por su parte, la API funciona con la autenticación estricta habilitada y sin exponer su documentación interactiva. En el \emph{dashboard}, las contraseñas son obligatorias y el inicio de sesión genera un \emph{token} de sesión con vencimiento. De esta manera, las credenciales de administración no se envían ni se almacenan en el navegador.

La figura~\ref{fig:despliegue-aws-apoyo} muestra los recursos de apoyo: el rol de la instancia, los parámetros con los secretos, el administrador de sesiones, el bucket de las versiones de la API y del \emph{dashboard} y, definidos en Terraform pero sin desplegar, CloudFront y el bucket del \emph{dashboard}. La instancia conserva la misma dirección IP cada vez que se enciende.

\subsection{Contenedores}
Durante el desarrollo se evalúa utilizar Docker Compose para ejecutar la API, Redis y el \emph{dashboard} en contenedores. Sin embargo, se descarta esta alternativa por tres razones. En primer lugar, el agente debe ejecutarse de forma nativa en Windows para acceder a los procesos y gestionar los permisos del sistema de archivos, por lo que no puede integrarse en este esquema de contenedores. En segundo lugar, Redis y PostgreSQL se reemplazan por servicios gestionados, lo que elimina la necesidad de ejecutarlos localmente. Por último, ejecutar la API como un servicio nativo en la instancia simplifica su administración mediante las herramientas del sistema operativo y del proveedor de nube.

La imagen de la API se conserva en el repositorio como alternativa de despliegue, aunque esta modalidad no forma parte del camino de despliegue verificado.

\subsection{Viabilidad técnica}
El sistema no requiere hardware específico para su funcionamiento. El agente se ejecuta como un proceso nativo en equipos con Windows que la organización ya posee y mantiene un consumo de recursos acotado, conforme a RNF-02. Por su parte, la API y el almacenamiento utilizan servicios de nube de propósito general, como cómputo, Redis y PostgreSQL gestionados, que pueden contratarse bajo demanda. Por lo tanto, la viabilidad técnica depende de la disponibilidad de estos servicios y de la infraestructura existente, sin necesidad de adquirir ni desarrollar dispositivos adicionales.

\section{Protocolos de comunicación}
\label{sec:protocolos}
La comunicación entre el agente, el \emph{dashboard} y la API utiliza HTTP/REST con mensajes en JSON. Cada evento se envía como una solicitud independiente y recibe su propia respuesta, por lo que no es necesario mantener una conexión persistente. Los contratos de datos se definen con Pydantic en la API y Zod en el \emph{dashboard}, lo que permite validar la estructura de los mensajes en ambos componentes. Las respuestas no cuentan con una firma propia, por lo que la integridad de los datos durante la transmisión depende de TLS (sección~\ref{sec:limitaciones-producto}).

El \emph{dashboard} actualiza el estado mediante consultas periódicas cada 2~s. Aunque el puntaje cambia con cada evento, los casos de uso no requieren notificaciones instantáneas, por lo que se descarta el uso de WebSockets. Esta alternativa habría requerido gestionar conexiones persistentes y mecanismos de reconexión sin aportar un beneficio proporcional a las necesidades del sistema.

La autenticación se apoya en claves enviadas en encabezados HTTP. Cada agente posee una clave propia, almacenada como \emph{hash}, revocable y ligada a su identificador y a los usuarios que puede reportar. El \emph{dashboard}, en cambio, inicia sesión con usuario y contraseña y recibe un \emph{token} de sesión opaco, con rol y vencimiento, que envía en cada solicitud. Las claves fijas de los niveles de acceso no salen del servidor y quedan reservadas para las herramientas de línea de comandos del administrador.

Para el almacenamiento, la API se comunica con Redis mediante RESP y utiliza transacciones optimistas para garantizar que las actualizaciones del estado de cada usuario se realicen de forma atómica ante eventos concurrentes. La conexión con PostgreSQL utiliza el protocolo estándar, un grupo de conexiones y tiempos de espera acotados.

Los servicios externos también se consumen mediante canales cifrados. La API se conecta por HTTPS con Gemini y el proveedor de identidad IAM, y se autentica ante Keycloak y Microsoft Entra ID mediante OAuth~2.0 con credenciales de cliente. El \emph{token} obtenido se mantiene en caché hasta su vencimiento. Las notificaciones, por su parte, se envían mediante SMTP con STARTTLS.

En la infraestructura de nube, el proxy inverso de la instancia termina las conexiones TLS tanto para el \emph{dashboard} como para la API, y el agente solo acepta URLs HTTPS cuando el destino no corresponde a una dirección de \emph{loopback}. En el despliegue local verificado, en cambio, el canal entre el agente y la API usa HTTP sin TLS sobre \emph{loopback}, lo que resulta aceptable en ese ámbito. Tampoco hay autenticación mutua por certificado entre ambos componentes, ya que el agente se autentica con su clave individual. Se declara como limitación (sección~\ref{sec:limitaciones-producto}) y queda diseñada como trabajo futuro (sección~\ref{sec:trabajo-futuro}).

\section{Síntesis}
\label{sec:sintesis-arquitectura}
La arquitectura separa la decisión, centralizada en la API, de la aplicación, distribuida en los agentes, siguiendo el modelo de Zero Trust. Las tecnologías se eligen por componente: Python para todo lo que toca al modelo, TypeScript para la interfaz y servicios gestionados para el almacenamiento. El sistema está verificado en un despliegue local; el despliegue en la nube está diseñado como código, con controles de seguridad explícitos, y aplicado con TLS terminado en la propia instancia, y se verifica de extremo a extremo con un agente real.
